# EventManager

Система из трёх независимых сервисов. У каждого своя база PostgreSQL. Подтверждение брони передаётся через Kafka: сервис броней публикует событие, сервис событий по нему уменьшает число свободных мест.

## Состав системы

| Сервис | Что делает | База в Docker | Порт |
|--------|------------|---------------|------|
| Users | Регистрация, вход, выдача JWT | `users` | http://localhost:5101 |
| Events | CRUD событий и учёт мест | `events` | http://localhost:5102 |
| Bookings | Создание и отмена броней, подтверждение | `bookings` | http://localhost:5103 |

Kafka доступна с хоста на `localhost:9092`. Внутри Docker сервисы подключаются к `kafka:29092`. Топик — `booking-confirmed`.

JWT выдаёт только Users. Events и Bookings проверяют тот же секрет, издателя и аудиторию (`EventManager`). Управление событиями (`POST`, `PUT`, `DELETE /events`) доступно роли `Admin`. Эндпоинты `/bookings` требуют аутентификации; идентификатор пользователя читается из claims.

Сервисы не вызывают друг друга по HTTP. Изменение мест происходит только при обработке сообщения из Kafka.

## Поток BookingConfirmed

1. Клиент создаёт бронь в Bookings (`POST /bookings`). Бронь сохраняется со статусом `Pending`.
2. Фоновый обработчик Bookings подтверждает бронь и сначала записывает статус `Confirmed` в базу броней.
3. После сохранения Bookings публикует `BookingConfirmed` в топик `booking-confirmed`. Ключ сообщения — идентификатор события, чтобы брони одного события обрабатывались по порядку.
4. Events подписан на этот топик (группа `events-service`). При получении сообщения он находит событие и уменьшает `AvailableSeats` на `SeatCount`.
5. Если события нет или свободных мест не хватает, сообщение пропускается с записью в лог. Подписчик из-за этого не останавливается.

В сообщении только то, что нужно подписчику: идентификаторы брони, события и пользователя, количество мест и момент подтверждения.

## Кеш

Кешируются два чтения сервиса Events. Срок жизни задаётся в `appsettings.json`: `Redis:EventTtlMinutes` и `Redis:TopEventsTtlMinutes`, оба равны 5. Этого хватает, чтобы повторные запросы не ходили в базу, и недостаточно, чтобы устаревшее значение жило долго, если инвалидация не успела выполниться.

| Ключ | Что хранит | Как обновляется |
|------|------------|-----------------|
| `event:{id}` | Одно событие для `GET /events/{id}` | Инвалидация при записи |
| `events:top10` | 10 событий с наибольшей долей проданных мест | Только TTL |

Топ-10 — рейтинговый агрегат. Небольшое устаревание для него некритично, а список меняется нечасто, поэтому сбрасывать его при каждой брони не нужно.

Для одного события устаревание заметно: название, даты и число мест должны совпадать с базой. Поэтому выбрана инвалидация при записи, а не обновление кеша вместе с базой. После `PUT` и `DELETE /events/{id}`, а также после списания или возврата мест ключ `event:{id}` удаляется. Следующий `GET` читает базу и записывает кеш заново.

Тот же ключ удаляет обработчик `BookingConfirmed`: он уменьшает `AvailableSeats` и только после сохранения в базу сбрасывает `event:{id}`. Список `events:top10` он не трогает.

Сначала сохраняется база, потом меняется кеш. Если процесс оборвётся между этими шагами, в базе уже новые данные. Устаревший ключ либо исчезнет по TTL в 5 минут, либо будет удалён следующей успешной записью. Следующий промах чтения снова заполнит кеш из базы.

Если Redis недоступен, Events всё равно запускается: `AbortOnConnectFail` выключен, ошибки кеша пишутся в лог и не прерывают запрос. Чтение идёт в базу. Ответ медленнее, потому что клиент ждёт таймаут соединения.

## Наблюдаемость

Каждый API пишет логи в консоль одной JSON-строкой через Serilog и отдаёт телеметрию через OpenTelemetry.

| Инструмент | Зачем | UI |
|------------|--------|----|
| Jaeger | Трейсы входящих HTTP-запросов, исходящих HTTP-вызовов и запросов EF Core | http://localhost:16686 |
| Prometheus | Сбор метрик ASP.NET Core и рантайма .NET с `/metrics` | http://localhost:9090 |
| Grafana | Дашборд latency, активных запросов и RPS | http://localhost:3000 |

Логин Grafana — `admin`, пароль — `admin`. Внутри Docker сервисы шлют трейсы на `http://jaeger:4317`. С хоста OTLP-приёмник Jaeger доступен на порту `4317`. Prometheus забирает метрики по `prometheus.yml` с `users-service:8080`, `events-service:8080` и `bookings-service:8080`.

Стек мониторинга поднимается вместе с остальной системой:

```bash
docker compose up -d --build
```

Дашборд лежит в `grafana/eventmanager-aspnet.json`. В Grafana добавьте источник Prometheus с адресом `http://prometheus:9090`, затем импортируйте этот JSON: Dashboards → New → Import.

## Запуск

Нужен Docker.

```bash
docker compose up -d --build
```

Команда читает `docker-compose.yml`, который подключает `docker-compose_14.yml`: Zookeeper, Kafka, Redis, Prometheus, Jaeger, Grafana, три базы PostgreSQL и три API. У Events строка подключения к Redis внутри сети — `redis:6379`. При старте каждый сервис применяет свою миграцию.

Swagger:

- http://localhost:5101/swagger
- http://localhost:5102/swagger
- http://localhost:5103/swagger

Остановка:

```bash
docker compose down
```

### Проверка сценария

1. `POST /auth/register` на Users с `"role": "Admin"`, затем `POST /auth/login`. В `data` придёт JWT.
2. В Swagger Events нажмите **Authorize** и вставьте токен без слова `Bearer`. `POST /events` создаёт событие. Запомните `totalSeats`: сразу после создания столько же свободных мест.
3. `POST /bookings` с `eventId` этого события. Ответ **202**, статус `Pending`.
4. Через несколько секунд `GET /bookings/{id}` показывает `Confirmed`.
5. `GET /events/{id}` показывает `availableSeats` на единицу меньше. Это результат обработки `BookingConfirmed` из Kafka.
